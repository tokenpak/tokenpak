# TokenPak v1.30.2 Release Log

## Scope

This patch release corrects license handling and moves the release identity to
1.30.2.

1. **License activation.** `tokenpak activate` no longer replaces an installed,
   current license when a different key is given. It leaves `license.json`
   unchanged and names `tokenpak deactivate`. The same key is accepted as
   already active; an expired or pending license can still be replaced.
2. **License status.** `tokenpak license` and `tokenpak features` honour
   `expires_at` and `grace_days`. An unreadable `expires_at` counts as expired.
3. **License writes and the daemon connection file.** License writes are
   serialized under one lock, and an unverified write never replaces a signed
   install, even with a matching key. The Pro daemon's connection file
   (`pro/daemon.sock-info`) is looked up under the selected TokenPak home
   instead of always under `~/.tokenpak`. Windows takes a real cross-process
   license lock and fails safe without one.
4. **Identity.** The license fixes change behavior, so they ship as 1.30.2, not
   as a rebuild of 1.30.1: pip treats two builds with the same version as
   identical and would not replace an installed 1.30.1. No symbol is added to
   or removed from the public API snapshot, so this is a patch release.
5. **Paired-upgrade check.** `scripts/release/paired_upgrade_gate.py` verifies
   that an OSS and Pro pair is the exact reviewed pair, before and after
   install. It is in the source tree only: it is not in either wheel and adds
   no runtime command.
6. **Public claims.** Four statements overstated what TokenPak does and are
   corrected. The package summary read "Cut LLM costs with deterministic
   context compression, smart routing, and cost tracking"; it now reads "Local
   proxy for coding agents that records each request and shows how far the
   session can go: measured usage, estimated cost, burn and runway." The SDK
   readme and package description claimed automatic token-cost cuts and an
   `npm install tokenpak` package that is not published; they now say the SDK
   is source-only and not on npm. The repository comparison page listed
   compression, smart routing and hard budget caps as default behavior; it now
   points to the comparison page on the documentation site. The README now
   describes forecasts as estimates shown as ranges that appear only for a
   model and effort combination with enough local history.

## Pairing with TokenPak Pro

TokenPak Pro 0.6.0 requires `tokenpak==1.30.2` and declares OSS 1.30.2 as both
its minimum and maximum supported version (TIP 1.0 unchanged). This narrows the
range Pro 0.5.2 declared (1.26.0 through 1.30.1). The range is not widened
until a wider range is tested. Pro 0.5.x stays with OSS 1.30.1 or earlier and
is not supported on 1.30.2.

## Upgrade and rollback

**OSS only, no Pro installed.** Run `pip install --upgrade tokenpak`. No
database migration, configuration change or data backup is required. The only
on-disk addition is an empty `license.json.lock` file that a license write
creates beside `license.json`.

**Pro 0.5.x installed.** Do not upgrade `tokenpak` alone. Keep the host on OSS
1.30.1 and Pro 0.5.x until Pro 0.6.0 is available, then upgrade the pair
together as below.

**Paired upgrade, OSS 1.30.2 with Pro 0.6.0.** Version constraints alone cannot
reject a mixed pair, for example new OSS with old Pro. The supported upgrade is
a paired one, in a fresh environment, with the gate script from the OSS source
tree. The gate checks release identity only; it is not full release approval.
It never installs anything, stops processes or touches license or state files.

1. Back up `license.json` before you start.
2. Get the manifest, a JSON file naming the exact reviewed pair:
   `{"oss": {"name", "version", "wheel_sha256"}, "paid": {"name", "version",
   "wheel_sha256"}}`. It comes with the release, never from whatever wheels
   happen to be present: it is the trust root, and the gate records its
   sha256. Pin the gate script itself to a reviewed commit or file sha256.
3. Check the wheels before installing anything. The wheel directory must hold
   exactly the two pinned wheels; a missing, extra, unknown or hash-mismatched
   wheel exits 1. This step never reports `ready: true`.

   ```bash
   python scripts/release/paired_upgrade_gate.py check-artifacts \
     --manifest manifest.json --wheel-dir wheels/ --receipt receipt.json
   ```

4. Create a new virtual environment, not the working one, so a failed or
   partial `pip` cannot damage the previous environment. Install both exact
   wheels from the wheel directory in a single `pip install` invocation.
5. Verify the install with that environment's own Python, immediately before
   you cut over. The gate compares every wheel file byte for byte with the
   installed copy, so a same-version no-op or a partial install exits 1. It
   also resolves each wheel's top-level imports without running application
   code and rejects any that land outside the verified install, such as a
   `PYTHONPATH` or source-checkout shadow. Only this step writes `ready: true`.

   ```bash
   staging-env/bin/python scripts/release/paired_upgrade_gate.py check-installed \
     --manifest manifest.json --wheel-dir wheels/ --receipt receipt.json
   ```

6. Quiesce old processes before the pair touches shared state (the license and
   state files). Old processes keep running old code; the gate cannot stop
   them or older direct writers.

Accept the pair only on a zero exit code and a current receipt with
`ready: true` whose manifest hash, `prefix`, `executable` and per-role wheel
hashes match the approved pair and the environment you will launch. The gate
invalidates the receipt at the start of every run; if it cannot write the
receipt the run exits 1, and no earlier receipt may be used. Launch only from
the verified environment: no `PYTHONPATH`, no source-checkout working
directory and no unreviewed editable or `.pth` entries. Edits made after the
check, including stale extra files, are not detected, so stage freshly and
make no manual writes. On Windows the license lock times out after 30 seconds;
on POSIX it blocks until released.

A failed run leaves the previous environment and the license bytes untouched.
Recover by discarding the staging environment, by running
`pip uninstall tokenpak-paid` to keep OSS only (the license file is not
touched), or by reinstalling the previous verified pair in one invocation.

**Rollback.** OSS only: `pip install tokenpak==1.30.1`; the leftover
`license.json.lock` file is ignored by 1.30.1. With Pro installed: switch back
to the previous environment, or reinstall the previous pair, OSS 1.30.1 and
Pro 0.5.2, in one `pip install` invocation and run the gate against that
pair's manifest. Never downgrade only one of the two packages. Rolling OSS
back removes the license fixes above. It does not undo licenses issued or
revoked in the meantime, and no database migration is involved.
