# TokenPak v1.30.2 Release Log

Local candidate. Nothing in this log means the version is published, tagged or
deployed.

## Scope

1. **License activation.** `tokenpak activate` no longer replaces an installed,
   current license when a different key is given. It leaves `license.json`
   unchanged and names `tokenpak deactivate`. The same key is accepted as
   already active; an expired or pending license can still be replaced.
2. **License status.** `tokenpak license` and `tokenpak features` honour
   `expires_at` and `grace_days`. An unreadable `expires_at` counts as expired.
3. **Shared-profile and Windows writers (already prepared on this branch).**
   License writes are serialized under one lock and an unverified write never
   replaces a signed install, even with a matching key. The license and daemon
   sock-info paths resolve through the shared path contract and stay inside the
   selected home. Windows takes a real cross-process license lock and fails
   safe without one. These are source-level and exact-artifact test results,
   not live verification.
4. **Identity.** The corrected build was previously labelled 1.30.1, the same
   version as the published release but with different bytes. pip treats such
   builds as identical, so it would not replace an installed 1.30.1. The
   version moves to 1.30.2. No public symbol is added or removed, so this is a
   patch release.

## Pairing with TokenPak Pro

Pro 0.6.0 requires `tokenpak==1.30.2` and declares OSS 1.30.2 as both its
minimum and maximum supported version (TIP 1.0 unchanged). This narrows the
range Pro 0.5.2 declared (1.26.0 through 1.30.1). The range is deliberately
not widened until a wider range is tested. Pro 0.5.x stays with OSS 1.30.1 or
earlier and is not supported on 1.30.2.

## Upgrade and rollback

Version constraints alone cannot reject a mixed pair, for example new OSS with
old Pro. The supported upgrade is a paired one, in a fresh environment:

1. Run `scripts/release/paired_upgrade_gate.py check-artifacts` against the
   approved manifest and the wheel directory **before** installing anything.
2. Install the two exact wheels, named by the manifest, in a single
   `pip install` invocation.
3. Run `check-installed` with the new environment's own Python.

Require a zero exit code and a current receipt with `ready: true` whose
target prefix, executable, manifest hash and per-role wheel hashes match the
approved pair. Old writers must be quiesced manually before the pair touches
shared state. The exact requirements are in the "Paired-upgrade gate
(fail-closed)" section of `docs/release-readiness-20261003.md`; they are not
repeated here.

The gate script is reviewed separately and delivered beside the wheels and the
manifest. It is not in either wheel and adds no runtime command. It verifies
release identity only; it is not full release approval.

Rollback is to switch back to the previous environment, which still holds the
retained corrected LOCAL OSS 1.30.1 / Pro 0.5.2 wheel pair. Those local wheels
are not the published bytes: the published 1.30.1 differs, and the bytes of any
private-index Pro 0.5.2 are unknown. Select by file hash, never by version
label. No database migration or configuration change is
involved and the gate never touches license or state files. Do not downgrade
only one of the two packages.

  is an outstanding integration/publication CI gate.
