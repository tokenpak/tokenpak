# TokenPak v1.31.0 Release Log

## Scope

This minor release shows an update that is installed but not yet running, adds a
safe way to load it, and makes `tokenpak home migrate` a real merge. It also
stops about a hundred places in the product from writing to the older home
folder after an install has moved to the new one.

1. **Pending update, shown.** `tokenpak status`, `tokenpak doctor` and the stats
   footer say when a newer version is staged or installed but not running, for
   example `1.30.3 → 1.31.0, applies at next launch`. The companion status line
   ends with `update <version> pending` when it fits, and is never clipped to
   make room. The check is local: a staged-release marker, or an installed
   version newer than the version the proxy reports on its loopback `/health`.
   `tokenpak update` reports a pending update instead of downloading it again.
2. **`tokenpak update apply`.** Restarts the TokenPak services so the pending
   version takes effect. It takes two idle observations a short interval apart
   (requests in flight, connections to the proxy and the Pro daemon, request
   counter and process unchanged) and checks again immediately before it stops
   anything. If a request is in flight or a client is connected it changes
   nothing and exits with code 9. `--check` is a dry run. With no service
   manager it prints the exact manual step.
3. **`tokenpak home migrate`, plan first.** It used to copy blindly. It now
   prints a plan by default and writes only with `--apply`, merging
   `~/.tokenpak` into `~/.tpk`:
   - SQLite databases are snapshotted and merged row by row; journal entries
     are matched on content, not on row id. A database with virtual tables is
     skipped when its content already matches, and otherwise the `~/.tpk` copy
     is kept and the older one is saved beside it as `<name>.legacy`.
   - A file that differs keeps the `~/.tpk` copy and the older one is saved
     beside it as `<name>.legacy`.
   - Every changed target is backed up first (a `backups/home-migrate-<time>`
     folder in `~/.tpk`).
   - Symbolic links are recreated, never followed; a relative link that stays
     inside the home is recreated as written.
   - `~/.tokenpak` is never modified or removed.
   - It refuses while the proxy or a companion session is in use.
   - A successful `--apply` writes `home-migrated.json` in `~/.tpk`.
4. **One home resolver.** Product code that built `~/.tokenpak` or `~/.tpk`
   paths itself kept writing the older home after an install moved, which split
   the install again. Those writers now use the resolver, and a test fails on a
   hard-coded home path in product code.
5. **Doctor reports the layout.** `tokenpak doctor` warns when both homes hold
   state ("split home: both homes hold state"), reports a finished migration
   ("migrated on <time>"), and warns again only if something wrote to the older
   home after the migration.
6. **Identity.** New commands and new behavior, so this is a minor release. The
   public API snapshot gains the new command modules and
   `tokenpak.core.runtime.update_pending` (30 symbols, additive; none removed
   or changed).

## Upgrade note: installs with state in both homes

If you have TokenPak state in both `~/.tokenpak` and `~/.tpk`, new writes go to
`~/.tpk` after you upgrade. Spend-cap, cost and telemetry history that lives in
`~/.tokenpak` can look reset until you run `tokenpak home migrate --apply`. Run
`tokenpak home migrate` first to read the plan; it changes nothing. `tokenpak
doctor` flags this layout. Installs with a single home are unaffected, and so
are installs that set `TOKENPAK_HOME`.

## Pairing with TokenPak Pro

TokenPak Pro 0.6.0 accepts only OSS 1.30.3 and refuses 1.31.0. Pro users stay on
1.30.3 and wait for Pro 0.6.1, which is tested against the exact 1.31.0 release
source before it is published. Do not upgrade `tokenpak` alone on a host with
Pro installed: pip does not stop it, `pip check` then fails, and Pro refuses to
run against the newer package. Upgrade the pair together once Pro 0.6.1 is
available.

## Upgrade and rollback

**OSS only, no Pro installed.** Run `pip install --upgrade tokenpak`. The
upgrade is package-only: no migration runs automatically, no configuration
change is needed, and no file is moved. A single-home install keeps resolving
to its home. A split home is flagged by `tokenpak doctor`, and you choose when
to run `tokenpak home migrate --apply`.

**Rollback.** `pip install tokenpak==1.30.3`. State written to `~/.tpk` after a
migration stays there, and the migration leaves `~/.tokenpak` as it was, so
1.30.3 reads both homes as before. With Pro installed, switch back to the
previous environment, or reinstall the previous pair in one `pip install`
invocation; never downgrade only one of the two packages.
