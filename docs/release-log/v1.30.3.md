# TokenPak v1.30.3 Release Log

## Scope

This patch release makes TokenPak find a license that is in the older home
folder, and moves the release identity to 1.30.3.

1. **License file lookup.** TokenPak keeps its files in `~/.tpk`, or in
   `~/.tokenpak` on an installation that predates it. Until now it chose one of
   the two folders for everything, by what that folder held. An installation
   whose `license.json` sat in `~/.tokenpak` while `~/.tpk` held other files
   (companion data, logs, the Pro daemon directory) therefore read as
   unlicensed: `tokenpak license` and `tokenpak features` showed the free plan,
   and `tokenpak activate` would have stored a new pending key in `~/.tpk` next
   to the installed license. The license file is now looked up on its own. With
   `TOKENPAK_LICENSE_FILE` and `TOKENPAK_HOME` unset, TokenPak uses
   `~/.tpk/license.json` if it exists, otherwise `~/.tokenpak/license.json`; if
   neither exists, a read uses the selected home and a first license is written
   to the home a new installation uses.
2. **Writes follow the file in use.** Activation, refresh and removal act on the
   file that was found, so a read and the write that follows name the same file,
   and the `license.json.lock` file is created beside it. `tokenpak activate`
   still refuses to overwrite an installed, current signed license, now
   including one in the other folder; the same key is still accepted as already
   active, and a pending license is replaced in place.
3. **Identity.** The fix changes behavior and 1.30.2 is already published, so it
   ships as 1.30.3. No symbol is added to or removed from the public API
   snapshot, so this is a patch release.

## Lookup order

| Setting | Read | Write |
|---|---|---|
| `TOKENPAK_LICENSE_FILE` set | that file | that file |
| `TOKENPAK_HOME` set | `<TOKENPAK_HOME>/license.json` only | `<TOKENPAK_HOME>/license.json` only |
| neither set, `~/.tpk/license.json` exists | `~/.tpk/license.json` | `~/.tpk/license.json` |
| neither set, only `~/.tokenpak/license.json` exists | `~/.tokenpak/license.json` | `~/.tokenpak/license.json` |
| neither set, no license in either folder | the selected home | the home a new installation uses |

With `TOKENPAK_HOME` set, the default folders are never consulted, so a
sandboxed run cannot see or replace a real license. If both default folders hold
a license file, the one in `~/.tpk` is used. The check is for a file, not for a
valid license. Every other file, including the Pro daemon connection file
(`pro/daemon.sock-info`), stays in the selected home, and nothing is moved,
copied or created by the lookup.

## Pairing with TokenPak Pro

TokenPak Pro 0.6.0 requires `tokenpak==1.30.3` and declares OSS 1.30.3 as both
its minimum and maximum supported version (TIP 1.0 unchanged). No Pro release
supports 1.30.2 or 1.30.3 yet, and Pro 0.5.x stays with OSS 1.30.1 or earlier.
The range is not widened until a wider range is tested.

## Upgrade and rollback

**OSS only, no Pro installed.** Run `pip install --upgrade tokenpak`. No
database migration, configuration change or data backup is required, and no file
is moved. If your license is in `~/.tokenpak` and `~/.tpk` holds other files,
`tokenpak license` now reports it.

**A pending key left by 1.30.2.** If you ran `tokenpak activate` on 1.30.2 in
that layout, `~/.tpk/license.json` holds a pending key and now takes precedence
over the license in `~/.tokenpak`. Run `tokenpak deactivate`: it removes the file
in use, and the license in `~/.tokenpak` then takes effect.

**Pro 0.5.x installed.** Do not upgrade `tokenpak` alone. Keep the host on OSS
1.30.1 and Pro 0.5.x until Pro 0.6.0 is available, then upgrade the pair
together.

**Paired upgrade, OSS 1.30.3 with Pro 0.6.0.** The procedure is the one in the
[1.30.2 release log](v1.30.2.md), with the 1.30.3 and 0.6.0 wheels. Version
constraints alone cannot reject a mixed pair, so the supported upgrade is a
paired one, in a fresh environment, with the gate script from the OSS source
tree at the `v1.30.3` tag (`scripts/release/paired_upgrade_gate.py`). The gate
checks release identity only; it is not full release approval. It never installs
anything, stops processes or touches license or state files.

1. Back up `license.json` before you start.
2. Get the manifest, a JSON file naming the exact reviewed pair. It comes with
   the release and is the trust root; the gate records its sha256.

   ```json
   {
     "oss": {"name": "tokenpak", "version": "1.30.3", "wheel_sha256": "<sha256 of the OSS wheel>"},
     "paid": {"name": "tokenpak-paid", "version": "0.6.0", "wheel_sha256": "<sha256 of the Pro wheel>"}
   }
   ```

3. Check the wheels before installing anything. This step never reports
   `ready: true`.

   ```bash
   python scripts/release/paired_upgrade_gate.py check-artifacts \
     --manifest manifest.json --wheel-dir wheels/ --receipt receipt.json
   ```

4. Create a new virtual environment and install both exact wheels from the wheel
   directory in a single `pip install` invocation.
5. Verify the install with that environment's own Python, immediately before you
   cut over. Only this step writes `ready: true`.

   ```bash
   staging-env/bin/python scripts/release/paired_upgrade_gate.py check-installed \
     --manifest manifest.json --wheel-dir wheels/ --receipt receipt.json
   ```

6. Quiesce old processes before the pair touches shared state, and launch only
   from the verified environment.

**Rollback.** OSS only: `pip install tokenpak==1.30.2`, or `1.30.1`; a leftover
`license.json.lock` file is ignored by 1.30.1. Rolling OSS back restores the old
lookup, so an installation in the split layout above reads as unlicensed again.
With Pro installed, switch back to the previous environment, or reinstall the
previous pair in one `pip install` invocation. Never downgrade only one of the
two packages. No database migration is involved.

## Validation and open requirements

**Focused checks on the change** (Python 3.12, a new virtual environment
installed editable from the branch, temporary files in memory-backed storage):

- License, licensing and path tests: 26 new tests cover the lookup table (no
  folders, canonical only, legacy only, split layout, a license in both,
  `TOKENPAK_HOME` set with and without a license, `TOKENPAK_LICENSE_FILE`),
  activation over a signed license in the other folder (refused, file
  unchanged), same-key re-activation, a pending key replaced in place with its
  lock beside it, removal, atomic replacement and owner-only permissions. 12 of
  them fail against the previous lookup.
- The existing license, licensing and path tests and every other test file that
  uses the path module or the license environment variables pass.
- `make release-gate-check` with the snapshot-generation variable unset passes:
  the public API, workflow-steps and telemetry-schema snapshots match, and the
  taxonomy check passes. No symbol is added to or removed from the public API
  snapshot.
- `ruff check` and `ruff format --check` pass on every changed Python file.

**Open requirements.**

- Pro 0.6.0's own CI pins the OSS source it tests; that pin moves to the 1.30.3
  release commit once it exists.
- The NLTK and Accelerate advisory disposition recorded for 1.30.2 was accepted
  for that release only and must be reassessed at this cut, together with the
  development-lock advisories listed in the 1.30.2 log.
- Not yet run: the built-artifact checks (wheel and sdist, leak scan, clean
  install, upgrade and rollback), the exact-head CI, publication, the
  documentation and site updates, and the watch period.
