# TokenPak v1.30.0 Release Log

## Backbone remediation and proxy-restart recovery signal

This candidate closes all 22 findings (3 Critical, 6 High, 10 Medium, 3 Low)
from the September 26 backbone forensic audit, plus one net-new capability: a
durable SQLite-backed execution ledger that gives an explicit
`terminally_failed` / `recovery_status` signal to a retried request after the
proxy restarts mid-stream, instead of a bare connection reset. This is a
fail-with-signal correction, not transparent replay or a full exactly-once
resume state machine.

The remaining 21 findings are backward-compatible correctness fixes: semantic
cache keys now include model identity, `tip_spend_guard.*` config rejects
unknown keys, spend-guard audit rows carry an explicit reason and
projected-token count on every decision path (including previously-unlabeled
hard-block branches), the background OAuth refresher is wired into the
thread-based proxy server, savings/compare/leaderboard reads are retargeted
off a stale schema path, vault-index load failures are surfaced instead of
silently printed, and duplicated legacy CLI shim modules (`tokenpak.agent.cli
.commands.{metrics,serve}`) are converted to thin deprecated re-exports of
their already-canonical implementations. None of these changed the public
CLI, HTTP, or configuration surface: the canonical CLI command modules
(`tokenpak.cli.commands.*`) that ship the live `tokenpak metrics` / `tokenpak
serve` commands were already in their current shape on the previously
published 1.29.0; the touched legacy modules are dead internal-only code with
no in-repo importer.

## Upgrade and rollback

This is an OSS-only candidate; no OSS storage schema, config format, or public
API changed. Pro 0.5.0's existing declared compatibility (OSS 1.26.0 through
1.29.0) is unaffected by anything in this diff — the touched Pro gating-table
code is internal documentation/guarding, not a contract change — but Pro has
not been independently re-run against 1.30.0 in this cycle; that re-verification
remains an open item before treating the pairing as re-tested.

Upgrade is a package-only upgrade: no database migration, no config change, no
data backup is required. Rollback is a plain downgrade to the previously
published 1.29.0 package.
